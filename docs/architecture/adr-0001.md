# ADR 0001 - Usar gRPC entre a API de Orquestração e o Planejador de Rotas

**Status:** Aprovado

## Contexto

Quando aparece um bloqueio, os AGVs afetados ficam parados até receberem uma rota nova. Então o recálculo precisa ser rápido.

A API de Orquestração é feita em Node.js e o Planejador de Rotas em Python (por causa da biblioteca NetworkX). Como são linguagens diferentes, já aconteceu de a gente errar nome de campo no JSON entre os dois lados.

Além disso, se o Planejador travar, a API não pode ficar esperando para sempre com o AGV parado.

Opções avaliadas:
- **REST com JSON:** mais simples, mas não tem um contrato fixo entre os dois serviços.
- **Mensageria (RabbitMQ):** aqui a API precisa da resposta na hora, e fazer pergunta e resposta por fila complica.
- **gRPC:** tem contrato definido em arquivo `.proto` e é mais rápido.

## Decisão

Usar **gRPC** entre a API e o Planejador. O contrato fica no arquivo `planejador.proto`:

```proto
service Planejador {
  rpc CalcularRota (RotaRequest) returns (Rota);
  rpc RecalcularRota (RecalculoRequest) returns (NovaRota);
}
```

O código dos dois lados é gerado a partir desse arquivo. Toda chamada de recálculo tem **prazo (deadline) de 2 segundos**: se passar disso, a API considera que não tem rota nova e avisa o operador.

## Consequências

- **Vantagens:** contrato igual nos dois serviços, comunicação mais rápida que REST e o prazo evita que o AGV fique parado esperando sem limite.
- **Desvantagens:** é mais difícil testar na mão (não dá para usar só o navegador, precisa de uma ferramenta como o grpcurl), e a equipe ainda está aprendendo a gerar o código a partir do `.proto`.
